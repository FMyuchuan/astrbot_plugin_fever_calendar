# 发烧云日程 —— 协议说明

本文记录「不依赖发烧手机读写发烧云日程」所用到的全部协议细节，均来自实测 + APK 反编译。

---

## 1. 登录

### 1.1 服务标识

| 项 | 值 |
|---|---|
| 日历 sid | `calendar` |
| 日历 STS | `https://api.comm.miui.com/calendar/sts` |
| 数据服务 sid | `micloud` |
| 数据 STS | `https://api.micloud.xiaomi.net/sts` |
| 账号域名 | `https://account.xiaomi.com` |

### 1.2 静默登录（推荐）

手上只要有 `passToken`，就不用再输密码：

```
GET https://account.xiaomi.com/pass/serviceLogin?sid=calendar&_json=true
Cookie: userId=...; cUserId=...; passToken=...
```

响应（去掉 `&&&START&&&` 前缀）：

```json
{
  "code": 0,
  "ssecurity": "xxxxxxxxxxxxxxxxxx==",
  "userId": 1234567890,
  "nonce": 5959996615319375872,
  "location": "https://api.comm.miui.com/calendar/sts?d=...&nonce=...&_ssign=..."
}
```

**关键坑**：`clientSign` 必须用响应里的**整数 nonce**，不是 `location` 里的 `nonce` 参数：

```python
clientSign = base64.b64encode(sha1(f"nonce={resp['nonce']}&{ssecurity}").digest()).decode()
url = location + ("&" if "?" in location else "?") + "clientSign=" + quote(clientSign)
```

跟着这个 URL 走一次，就会拿到：

- `serviceToken`（日历服务用）
- `calendar_slh`、`calendar_ph`（日历专用会话 cookie）

`micloud` 的 token 来自 `sid=micloud`，用于 pdc 数据接口。

### 1.3 密码登录（备用）

`GET /pass/serviceLogin` 取 `_sign`/`qs`/`callback`，再
`POST /pass/serviceLoginAuth2`，`hash = MD5(密码).upper()`。
国内新设备大概率触发「身份二次确认」，此时改用扫码：

```
GET https://account.xiaomi.com/longPolling/loginUrl?sid=calendar&_json=true
```

返回 `qr`（二维码内容）与 `lp`（轮询地址），手机确认后从 `lp` 取 `location`。

## 2. 数据接口

```
GET https://pdc.micloud.xiaomi.net/mic/pdc/v4.1/apps/calendar/spaces/default/records
```

### 2.1 必带参数

| 参数 | 说明 |
|---|---|
| `_nonce` | 8 字节随机数的 Base64 |
| `_count` | 并发/批次，实测 3 可用 |
| `_delta` | 增量步长，实测 2 |
| `_backend` | `false` |
| `_apkversioncode` | `112000200` |
| `_apkversion` | `1.12.0.2.00` |
| `limit` | 游标，见 §3 |
| `syncToken` | 游标，见 §3 |
| `signature` | 见 §2.2 |

### 2.2 签名

```python
items = ["GET", "/mic/pdc/v4.1/apps/calendar/spaces/default/records"]
items += [f"{k}={v}" for k, v in sorted(params.items())]   # TreeMap 顺序
items += [ssecurity]
signature = base64.b64encode(sha1("&".join(items).encode()).digest()).decode()
```

来源：`com.miui.micloudsync` 的 `LY/g;->h` → `Lh0/d;->h` → `Lh0/f;->b`。

### 2.3 必带 Cookie

```
Cookie: serviceToken=<micloud token>; userId=...; cUserId=...
```

只带签名、不带 cookie 会得到 `401`（`WWW-Authenticate: Basic realm="default"`）。
两者都带才放行。

## 3. 游标（limit / syncToken）

游标是 **AES 加密的不透明串**，格式与响应体一致：

```
1:<urlsafe_b64(iv)>:<urlsafe_b64(ciphertext)>
```

- 算法：`AES/CBC/PKCS5Padding`
- key：`base64decode(ssecurity)`
- iv：加密时随机 16 字节，放在第 2 段
- 明文：`limit` 是十进制数字（如 `"20"`）；`syncToken` 是上次响应里返回的原样字符串

因为密钥由 ssecurity 推导，**可以自己造游标**，这是绕开「必须先有上一页」的关键：

```python
def make_token(key, plain: bytes) -> str:
    iv = os.urandom(16)
    ct = AES.new(key, AES.MODE_CBC, iv).encrypt(plain + bytes([pad]) * pad)
    return f"1:{b64u(iv)}:{b64u(ct)}"
```

`limit=0` 会被拒绝（`10008 invalid limit: 0`），`limit` 缺失是 `10016 缺失必选参数`。

---

## 4. 响应

```json
{"S": "...", "D": "1:<iv>:<ciphertext>", "V": "V1"}
```

`D` 解密后：

```json
{
  "result": "ok",
  "code": 0,
  "data": {
    "syncToken": "GBIxOTE0NDI0Nzg0MTUwMjg5OTIYGEZySz...",
    "watermark": 191442478415028992,
    "records": [ ... ]
  }
}
```

注意：解密结果尾部会带填充字节，解析时用 `raw_decode` 或先裁掉。

## 5. 记录结构

```json
{
  "creationTime": 1648817698181,
  "modificationTime": 1649595082563,
  "uniqueKey": "calendar_displayname_xiaomi,1234567890",
  "eTag": 137080952045242624,
  "contentJson": {
    "title": "……",
    "dtstart": 1648818000000,
    "dtend": 9223372036854775807,
    "duration": "P3600S",
    "allDay": 0,
    "rrule": "FREQ=WEEKLY;UNTIL=20220408T125959Z;WKST=SU;BYDAY=FR",
    "reminders": [{"method": 1, "minutes": 15}, {"method": 1, "minutes": 0}],
    "eventTimeZone": "Asia/Shanghai",
    "eventStatus": 1,
    "organizer": "1234567890",
    "isOrganizer": 1
  }
}
```

约定：

- `dtend == Long.MAX_VALUE` 时，结束时间 = `dtstart + duration`
- `eventStatus`：`1` 正常、`2` 已删除（墓碑记录，做双向同步时必须保留）
- 日历本身也是一条 record：`calendarDisplayName`、`calendarColor`、`isPrimary`、`calendarAccessLevel`
- `eTag` 是乐观锁，写操作要靠它做冲突检测

## 6. 写入接口

| 操作 | 方法与路径 | 参数（全部为 AES token） |
|---|---|---|
| 新增 | `POST /records` | `record` = AES(JSON 记录) |
| 修改 | `POST /records/{id}/update` | `record` = AES(JSON 记录)、`eTag` = AES(eTag) |
| 删除 | `POST /records/{id}/delete` | `type` = AES("event")、`eTag` = AES(eTag) |

记录 JSON 形如：

```json
{"type": "event", "parentId": "<日历 id>", "contentJson": {"title": "...", "dtstart": 1792843200000, "dtend": 1792846800000, "allDay": 0, "eventTimeZone": "Asia/Shanghai", "eventStatus": 1, "availability": 0, "accessLevel": 0, "hasAlarm": 0, "reminders": [{"method": 1, "minutes": 15}]}}
```

坑：

- 新增时带 `eTag` 会报 `eTag cannot be set`
- 新增时带 `id` 会报 `custom record id is not supported`
- 删除缺 `type` 报 `type参数不能为空`，缺 `eTag` 报 `eTag参数不能为空`
- `type` 和 `eTag` 都必须是加密 token，明文会 500
- 修改走 `/records/{id}/update`，`record` 里**不要**带 `eTag` 字段，`eTag` 单独作为参数传
- 改完 `eTag` 会变，返回值里有新的 `eTag`，下次修改要用新的

### 6.1 重复事件的单次例外

「只改这一次 / 只删这一次」不是改母事件，而是**新增一条例外记录**：

```json
{
  "type": "event",
  "parentId": "<日历 id>",
  "contentJson": {
    "title": "改过的标题",
    "dtstart": 1792890000000,
    "dtend": 1792891800000,
    "eventStatus": 1,
    "originalServerId": "<母事件 id>",
    "originalInstanceTime": 1792890000000,
    "originalAllDay": 0
  }
}
```

- 例外记录**不带 `rrule`**
- 删除某次用 `eventStatus: 2`
- 手机端会把它落成 `original_id` 关联的实例例外，删除的那次在日历里不再显示

## 7. 错误码

| code | 含义 |
|---|---|
| 10016 | 缺失必选参数（如 limit） |
| 10008 | 参数错误（如 `invalid limit: 0`） |
| 10011 | 服务端 RPC 错误（如 `records/0` 这种索引式路径） |
| HTTP 401 | 缺 cookie 或签名错 |
| HTTP 500 | 参数组合不合法（如 limit 传数字） |
